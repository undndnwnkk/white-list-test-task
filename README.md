# CRM: учёт звонков и назначение встреч

REST API для отдела, который обзванивает организации и назначает встречи менеджерам.
Тестовое задание Б (Software Developer) для WhiteList & Co Ltd.

**Стек:** Go 1.26 (стандартный `net/http`), PostgreSQL 16, `pgx`, миграции `goose`, Docker Compose.

---

## Быстрый старт

Нужны только **Docker** и **Docker Compose v2** (`docker compose version` ≥ 2.20). Локально Go не нужен.

```bash
git clone https://github.com/undndnwnkk/white-list-test-task.git
cd white-list-test-task
docker compose up --build -d --wait
```

API доступен на `http://localhost:8080`. Миграции и тестовые менеджеры применяются автоматически при старте приложения.

Проверка, что всё поднялось:

```bash
curl -s "http://localhost:8080/companies"
# {"items":[],"total":0,"limit":20,"offset":0}
```

Остановить: `docker compose down`. Остановить и удалить данные БД: `docker compose down -v`.

### Если порт занят

По умолчанию API публикуется на `8080`, PostgreSQL на `5433` (не `5432`, чтобы не конфликтовать с локальным Postgres). Оба порта можно поменять:

```bash
APP_PORT=9090 DB_PORT=55432 docker compose up --build -d --wait
```

Те же переменные можно положить в файл `.env` (пример в `.env.example`), Docker Compose и Makefile читают его автоматически.

## Тесты

**Вариант 1: только Docker** (рекомендуется):

```bash
docker compose run --rm --build tests
```

Команда поднимет PostgreSQL (если он ещё не запущен), соберёт образ с тестами и прогонит `go test ./...`.

**Вариант 2: локальный Go 1.26+:**

```bash
make test
```

`make test` сам поднимет PostgreSQL в Docker (`docker compose up -d --wait postgres`) и запустит `go test -count=1 ./...`.
Без `make`: `docker compose up -d --wait postgres`, затем
`TEST_DB_DSN='postgres://crm:crm@localhost:5433/crm_test?sslmode=disable' go test -count=1 ./...`.

Тесты **не трогают рабочую базу `crm`**. Каждый тестовый пакет сам создаёт свою базу (`crm_test_service`, `crm_test_repository`, `crm_test_httpapi`), накатывает на неё миграции и очищает перед каждым тестом. Поэтому пакеты можно гонять параллельно, а на свежем Postgres ничего готовить вручную не нужно.
Если `TEST_DB_DSN` не задан, интеграционные тесты пропускаются (`SKIP`). Unit-тесты выполняются в любом случае.

## API

Все времена в запросах и ответах в **UTC, ISO 8601** (`2030-01-07T05:00:00Z`). Рабочие часы проверяются по **Asia/Almaty (UTC+5)**: `05:00Z` это 10:00 по Алматы.

| Метод | Путь | Назначение | Успех |
|---|---|---|---|
| `POST` | `/companies` | добавить организацию `{name, bin, phone}` | 201 |
| `GET` | `/companies?status=&limit=&offset=` | список с фильтром по статусу и пагинацией | 200 |
| `POST` | `/calls` | результат звонка `{company_id, manager_id, result, meeting_id?}` | 201 |
| `POST` | `/meetings` | назначить встречу `{company_id, manager_id, start_at}` | 201 |
| `PATCH` | `/meetings/{id}` | перенести `{start_at}` или отменить `{status: "cancelled"}` | 200 |
| `GET` | `/meetings/{id}` | встреча с историей изменений (дополнительный эндпоинт) | 200 |
| `GET` | `/managers/{id}/schedule?date=YYYY-MM-DD` | расписание менеджера на день (день по Алматы) | 200 |

- **Статусы организации:** `new` (при создании), затем результат последнего актуального звонка: `no_answer`, `refused`, `meeting_set`.
- **Пагинация:** `limit` от 1 до 100 (по умолчанию 20), `offset` ≥ 0. В ответе `items`, `total`, `limit`, `offset`. Сортировка: сначала новые.

### Формат ошибок

Любой отказ возвращает JSON с машиночитаемым кодом и понятным сообщением:

```json
{"error": {"code": "outside_working_hours", "message": "meeting must fit within working hours: Mon-Fri 09:00-18:00 Asia/Almaty"}}
{"error": {"code": "validation_error", "message": "is required when result is meeting_set: create the meeting first", "field": "meeting_id"}}
```

| HTTP | Когда | Коды |
|---|---|---|
| 400 | невалидный запрос: JSON, типы, обязательные поля, формат БИН, телефона, даты, UUID, неизвестные поля | `validation_error` (+ `field`) |
| 404 | организация, менеджер или встреча не найдены | `company_not_found`, `manager_not_found`, `meeting_not_found` |
| 409 | конфликт с текущим состоянием | `bin_already_exists`, `manager_busy`, `company_busy`, `company_has_active_meeting`, `meeting_cancelled`, `meeting_already_started`, `meeting_already_linked` |
| 422 | запрос корректен, но нарушает бизнес-правило | `outside_working_hours`, `meeting_in_past`, `meeting_company_mismatch`, `invalid_data` |
| 500 | только непредвиденные сбои; детали пишутся в лог, наружу не отдаются | `internal_error` |

## Бизнес-правила и как они обеспечены

Каждое правило проверяется в сервисном слое (чтобы дать понятную ошибку). Те правила, которые можно выразить ограничением, дополнительно защищены в PostgreSQL: это страховка от гонок и от ошибок в коде.

| # | Правило | Сервис | БД |
|---|---|---|---|
| 1 | Встреча длится 60 минут | `end_at` вычисляется сервером, клиент передаёт только `start_at` | `CHECK (end_at = start_at + 60 min)` |
| 2 | Пн–пт 09:00–18:00 Asia/Almaty, встреча умещается целиком | `service.ValidateWorkingHours` | — |
| 3 | У менеджера нет пересекающихся встреч, стык не конфликт | — | `EXCLUDE USING gist (manager_id =, tstzrange(start,end,'[)') &&) WHERE scheduled` |
| 4 | У организации нет двух активных встреч | блокировка строки компании `FOR UPDATE` + проверка активной встречи | `EXCLUDE` на пересечение по `company_id` |
| 5 | `meeting_set` без встречи — ошибка | `meeting_id` обязателен, встреча существует, принадлежит той же компании и не отменена | `CHECK ((result = 'meeting_set') = (meeting_id IS NOT NULL))`, уникальность `meeting_id` |
| 6 | Перенос не теряет историю | при создании, переносе и отмене пишется событие | `original_start_at` (не меняется) + таблица `meeting_events` |
| 7 | Понятные ошибки, а не 500 | доменные ошибки превращаются в HTTP-коды в одном месте (`httpapi/errors.go`) | нарушения ограничений превращаются в доменные ошибки (`repository/errors.go`) |

Одновременное назначение на один слот: проигравшая транзакция получает нарушение `EXCLUDE`-ограничения и ответ `409 manager_busy`. Подробнее в `REFLECTION.md`.

## Принятые решения (где задание допускает разные трактовки)

1. **«Активная встреча» организации** — это любая неотменённая встреча, которая ещё не закончилась (`status = scheduled AND end_at > now`). Значит, у организации не может быть второй запланированной встречи, даже если она не пересекается по времени с первой: для CRM-воронки «одна организация — одна текущая договорённость». Пересечение встреч одной организации дополнительно запрещено на уровне БД.
2. **Порядок «встреча → звонок».** Сначала создаётся встреча (`POST /meetings`), потом фиксируется звонок с `result: meeting_set` и `meeting_id`. Так правило 5 проверяется буквально: звонок ссылается на существующую встречу. Одна встреча может быть результатом только одного звонка.
3. **Статус организации** равен результату последнего звонка. При отмене встречи звонок, который к ней привёл, перестаёт учитываться: статус пересчитывается по предыдущему звонку, а если звонков нет, становится `new`.
4. **История переноса**: поле `original_start_at` (когда встреча была назначена изначально) и журнал `history` с событиями `created`, `rescheduled`, `cancelled` и временем каждого изменения. Журнал отдаётся в ответе `PATCH` и в `GET /meetings/{id}`.
5. **Что можно менять.** Нельзя назначить или перенести встречу в прошлое. Нельзя изменить уже начавшуюся или отменённую встречу (409). Перенос и отмена делаются разными запросами: если в PATCH переданы оба поля, это 400.
6. **Точность времени:** `start_at` должен быть кратен минуте. Секунды отклоняются, чтобы `09:59:59` не превращалось в «почти 10:00».
7. **Расписание на день** — это календарный день по Алматы (`date=2030-01-07` означает интервал `2030-01-06T19:00Z`–`2030-01-07T19:00Z`), только неотменённые встречи.
8. **Праздники** не учитываются: рабочие дни — это просто пн–пт.
9. **Менеджеры** заводятся миграцией, эндпоинта для них в задании нет.

## Что сделано и что нет

**Сделано**
- Все 6 эндпоинтов из задания и `GET /meetings/{id}` для просмотра истории.
- Все 7 бизнес-правил: в сервисе и, где возможно, ограничениями PostgreSQL.
- Время в UTC, рабочие часы по Asia/Almaty (tzdata встроена в бинарник, от ОС не зависит).
- Миграции, запуск одной командой (`docker compose up`), тесты одной командой (в том числе без локального Go).
- Unit- и интеграционные тесты, включая обязательные (пересечение встреч, граница рабочего дня) и тест на одновременную запись.
- Примеры запросов: `requests.http` и `scripts/smoke.sh`.

**Не сделано / сознательно упрощено**
- Нет CRUD для менеджеров, они создаются миграцией.
- Праздники и сокращённые дни не учитываются.
- Нет списка звонков и встреч организации (`GET /companies/{id}/calls`), в задании не требуется.
- Нет авторизации, ролей, уведомлений и кэша: в задании прямо сказано, что они не нужны.
- Нет OpenAPI-спецификации, вместо неё таблицы выше и `requests.http`.
